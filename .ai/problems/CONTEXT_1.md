# Структурированная задача на переработку LLM-аудита

## Цель

Переработать текущую архитектуру LLM-аудита системы таким образом, чтобы:

* основной агент выполнял роль координатора/дирижера аудита;
* выполнение отдельных фаз аудита делегировалось специализированным субагентам;
* каждая фаза аудита была вынесена в отдельный шаблон (`.md`);
* шаблоны поддерживали параметризацию через контекст;
* систему можно было масштабировать, дополнять новыми фазами и запускать фазы независимо;
* итоговый аудит стал глубже, а не поверхностным.

---

# Основная проблема текущей реализации

Сейчас аудит реализован как одна большая задача с большим количеством фаз.

Из-за этого:

* агент теряет глубину анализа;
* контекст размазывается между этапами;
* аудит выполняется формально;
* сложно расширять и поддерживать отдельные части;
* невозможно переиспользовать отдельные фазы аудита независимо.

---

# Целевая архитектура

## Общая идея

Нужна многоагентная архитектура аудита:

### 1. Главный агент

Главный агент:

* собирает контекст по системе;
* управляет фазами аудита;
* подготавливает задачи;
* передает задачи субагентам;
* валидирует результаты;
* собирает финальный отчет.

### 2. Субагенты

Каждый субагент:

* отвечает только за одну фазу аудита;
* получает специализированный контекст;
* выполняет глубокий анализ своей области;
* возвращает результат;
* формирует часть отчета.

# Новый процесс аудита

## Этап 1. Загрузка контекста

Главный агент:

* загружает документацию;
* анализирует структуру проекта;
* собирает команды запуска;
* собирает docker-команды;
* собирает test-команды;
* собирает информацию о сервисах;
* собирает информацию о runtime и окружении.

Примеры контекста:

структура директорий;
README;
docker-compose;
Makefile;
CI/CD;
команды запуска;
env configuration;
API структура;
dependency graph.


---

## Этап 2. Запуск фаз аудита в цикле 

Главный агент читает папку с фазами аудита и для каждого шаблона  
в цикле Для каждой фазы:

Загружается шаблон фазы аудита `.md` шаблоны;
В шаблон подставляется контекст;
Формируется задача;
Задача передается субагенту;
Субагент выполняет аудит;
Возвращает результат;
Основной агент валидирует результат;
Результат добавляется в общий аудит.

---

## Выполнение фазы субагентом

Субагент:
* выполняет аудит своей области;
* формирует находки;
* записывает результаты в отдельный отчет;
* возвращает путь к отчету главному агенту.

# Этап 3. Финальная сборка отчета

Главный агент:

* объединяет результаты всех фаз;
* формирует единый аудит;
* устраняет дубли;
* проверяет консистентность итогового отчета.

# Требования к структуре файлов

## Структура директорий

```text
/audit-system
  /roles
    orchestrator.md
    specialist.md

  /audit-phases/
	├── 01-architecture-audit.md
	├── 02-backend-audit.md
	├── 03-frontend-audit.md
	├── 04-tests-audit.md
	├── 05-security-audit.md
	├── 06-devops-audit.md
	└── ...

  /templates
    final-report.md
    findings.md

```

---

# Требования к шаблонам фаз аудита

Каждая фаза должна быть отдельным `.md` файлом.

---

## Формат шаблона фазы

```md
# Audit Phase: Backend Audit

## Goal
Проверить backend-архитектуру, FastAPI endpoints, dependency injection, security и качество кода.

## Context
{SYSTEM_CONTEXT}

## Project Structure
{PROJECT_STRUCTURE}

## Commands
{AVAILABLE_COMMANDS}

## Expected Output
- список находок
- уровень критичности
- рекомендации
- потенциальные риски

## Report Format
{REPORT_TEMPLATE}
```

---

# Требования к параметризации

Все шаблоны должны поддерживать вставку контекста через placeholder'ы:

```text
{SYSTEM_CONTEXT}
{PROJECT_STRUCTURE}
{AVAILABLE_COMMANDS}
{DOCKER_COMMANDS}
{TEST_COMMANDS}
{REPORT_TEMPLATE}
{PHASE_NAME}
```

---

# Важное архитектурное требование

## Фазы должны запускаться независимо

Необходимо обеспечить возможность:

* запускать весь аудит целиком;
* запускать отдельную фазу независимо;
* переиспользовать фазы между проектами.

Примеры:

* только backend audit;
* только test audit;
* только security audit.
