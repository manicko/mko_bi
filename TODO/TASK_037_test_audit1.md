## 38. Аудит качества тестов (обязательно)

Цель:
- Провести аудит существующих тестов (`tests/`)
- Составить план действий для приведения их к уровню, когда каждый тест проверяет конкретное бизнес-правило, покрывает краевые случаи и имеет диагностическую ценность.
Определить, являются ли тесты полезными, проверяют ли они реальное поведение системы и способны ли обнаруживать регрессии.

### Проверить anti-patterns

#### Overmocking

Найти тесты, где:

* mock полностью заменяет бизнес-логику
* assertions проверяют значения из mock
* тест не проверяет реальное поведение

Признаки:

* большое количество patch/mock
* отсутствие проверки side-effects
* отсутствие интеграции между слоями

---

#### Tautological tests

Найти тесты, которые:

* повторяют реализацию
* проверяют очевидные вещи
* подтверждают текущее поведение вместо ожидаемого контракта

---

#### Wrong abstraction level

Найти тесты, которые:

* тестируют implementation details
* private methods
* внутренние SQL/ORM детали
* порядок вызова внутренних функций вместо результата

---

#### Weak assertions

Найти:

* отсутствие meaningful assertions
* assert True
* проверки только status_code
* отсутствие проверки данных/состояния

---

#### Fragile tests

Найти тесты, которые:

* ломаются при рефакторинге без изменения поведения
* зависят от internal structure
* используют sleep/time dependence
* зависят от порядка запуска

---

#### Dead tests

Найти:

* тесты, не проверяющие ничего полезного
* тесты без mutation resistance
* дублирующие тесты

---

### Mutation-анализ (логический)

Для каждого важного теста оценить:

* упадёт ли тест при изменении условий
* обнаружит ли:

  * смену оператора
  * удаление проверки
  * неверную агрегацию
  * возврат None
  * неправильную фильтрацию

Если тест остаётся зелёным при логической поломке — пометить как useless.

---

### Проверить test pyramid

Проверить баланс:

* unit
* integration
* e2e

Отметить:

* отсутствие integration tests
* чрезмерное количество unit tests с mock
* отсутствие real DB/API tests

---

### Проверить тестовую архитектуру

Проблемы:

* copy-paste tests
* giant fixtures
* hidden dependencies
* shared mutable state
* неявные setup/shutdown
