# TASK_033: Анализ соответствия кода ТЗ и выявление архитектурных проблем

## Цель

Провести аудит проекта на предмет:
1. **Полноты реализации ТЗ** (`SPEC.md`) — какие требования выполнены, какие нет, какие частично.
2. **Архитектурных проблем** — нарушение слоёв, жёсткие связи, циклические зависимости, неиспользуемые абстракции.
3. **Проблем в коде** — дублирование, игнорирование ошибок, неправильная работа с транзакциями, потенциальные утечки памяти/ресурсов, небезопасная работа с файлами, отсутствие валидации.
4. **Проблемы typing** — проверка ruff mypy

## Что проверить (чек-лист)

### 1. Полнота по SPEC.md
- [ ] Загрузка CSV (сжатый gz) — есть эндпоинт, обработка, удаление временных файлов.
- [ ] Обработка через Polars — трансформации, агрегации (groupby, YoY, доли).
- [ ] Хранение агрегатов в PostgreSQL (таблицы: `aggregated_data`, `dashboards`, `layouts`, `graphs`, `filters`, `processing_configs`).
- [ ] JWT + bcrypt — защита всех API, роли (`admin`, `editor`, `viewer`), проверка доступа на каждый запрос.
- [ ] Dash + Plotly — дашборды, фильтры, типы графиков (bar, line, pie, table), multi-axis, YoY.
- [ ] Логирование (upload, processing, errors, access).
- [ ] проверка ruff mypy всех файлов

### 2. Архитектурные проблемы
- [ ] **Смешение ответственности** — например, бизнес-логика в API-роутах, SQL-запросы в сервисах, валидация в моделях БД.
- [ ] **Циклические импорты** — проверить через `pytest --import-mode=importlib` или статический анализатор.
- [ ] **Неиспользуемые абстракции** — классы/функции, которые созданы, но нигде не вызываются (dead code).
- [ ] **Слабая изоляция слоёв** — прямое использование `db_session` в API-роутах, минуя сервисы.
- [ ] **Глобальные состояния** — синглтоны, конфиги, изменяемые модульные переменные.
- [ ] **Отсутствие интерфейсов** — везде конкретные реализации, сложно тестировать и заменять.
- [ ] **Нарушение Dependency Inversion** — высокоуровневые модули зависят от низкоуровневых через конкретные классы.

### 3. Проблемы в коде
- [ ] **Обработка ошибок** — голые `except: pass`, отсутствие логирования ошибок, неправильные статус-коды.
- [ ] **Транзакции** — нет явного commit/rollback при ошибках, гонки при конкурентной загрузке.
- [ ] **Безопасность** — SQL-инъекции (если есть raw SQL), инъекции в CSV (команды), отсутствие rate limiting.
- [ ] **Работа с файлами** — незакрытые дескрипторы, не удаляется временный файл при ошибке.
- [ ] **Производительность** — загрузка всего CSV в память, отсутствие batch-обработки, N+1 запросов к БД.
- [ ] **Конфигурация** — хардкод путей, параметров, секретов.
- [ ] **Типизация** — массовое использование `Any`, отсутствие `Optional` где нужно.
- [ ] **Документация** — отсутствуют docstring для сложных функций, непонятные названия переменных.

## Методология аудита

1. **Статический анализ** — прогон через `ruff`, `mypy`.
2. **Ручной обзор** ключевых директорий: `src/mko_bi/api/`, `services/`, `data/processing/`, `db/repositories/`, `dashboards/`.
3. **Сравнение с SPEC.md** — построчно отметить, что реализовано.
4. **Поиск «SMELL» **:
   - `# TODO`, `# FIXME`, `pass`, `...`, `except Exception`.
   - длинные функции (>50 строк).
   - глубокие вложенности (>4 уровня).
   - повторяющиеся блоки кода.
