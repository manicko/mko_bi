```markdown
# Техническое задание на аудит тестового покрытия
## «Соответствие тестов актуальной архитектуре и реализации»

### 1. Цель аудита
Выявить тесты, которые:
- отражают **устаревшую архитектуру** (синхронные вызовы вместо асинхронных, `int` вместо `UUID`, старые форматы данных);
- требуют **переписывания production-кода** ради прохождения тестов (или сохранения legacy-поведения);
- проверяют **неактуальные контракты** (API, DTO, репозитории, бизнес-правила);
- **противоречат текущей реализации** системы и тем самым блокируют рефакторинг.

**Основной принцип:**  
`production-архитектура и бизнес-правила являются источником истины`.  
Тесты должны адаптироваться под систему, а не наоборот.  
Запрещено изменять production-код только для прохождения устаревших тестов.

### 2. Объект аудита
- Все тесты (модульные, интеграционные, API, e2e) для сервиса на **FastAPI + PostgreSQL**.
- Тестовые фикстуры, фабрики данных, моки, хелперы.
- Конфигурация тестового окружения (БД, event loop, HTTP клиенты).
- CI/пайплайн запуска тестов.

### 3. Архитектурные инварианты (эталон для проверки)

| Область | Инвариант |
|---------|------------|
| **Асинхронность** | Любой I/O (БД, сеть, файлы) реализован как `async def`. Тесты обязаны вызывать такие функции через `await` в асинхронном контексте (`@pytest.mark.asyncio`). |
| **Идентификаторы** | Все первичные и внешние ключи — `UUID` (v4). `Integer` не допускается в тестовых данных, фикстурах, `assert`. |
| **БД (PostgreSQL)** | Типы колонок в тестовой БД совпадают с продакшен-схемой (миграции). Нет подмены генерации ID на автоинкремент. |
| **API слой** | Тесты эндпоинтов используют `httpx.AsyncClient`. Синхронный `requests` или `TestClient` без async запрещён. |
| **Слои приложения** | Бизнес-логика не должна тестироваться через роуты (только через сервисы). Тесты не проверяют внутренние детали реализации (implementation details). |
| **Контракты DTO** | Pydantic схемы в тестах совпадают с актуальными. Нет проверки устаревших полей. |

### 4. Что именно проверять (категории проблемных тестов)

#### 4.1. Тесты, использующие устаревший sync/async контракт
- Вызывают синхронно функцию, которая стала `async`.
- Используют обычный (синхронный) `TestClient` для async API.
- Не используют `await` для async методов.
- Обходят async lifecycle приложения (например, вызывают `asyncio.run()` внутри теста).
- Добавляют синхронные обёртки (`async_to_sync`) в прод-код ради тестов.

#### 4.2. Тесты, использующие устаревшие типы данных
- `Integer` ID вместо `UUID` (фикстуры, параметризация, assert).
- `pandas.DataFrame` там, где прод перешёл на `polars`.
- Старые структуры DTO / Pydantic схем (лишние поля, другие типы).
- Устаревшие поля моделей (например, `created_at` как `str` вместо `datetime`).
- Старые форматы API request/response (отсутствие новых обязательных полей).

#### 4.3. Тесты, проверяющие старую архитектуру
- Ожидают бизнес-логику внутри routes/controllers (после выноса в сервисы).
- Ожидают прямой доступ к БД из API слоя (когда используются репозитории).
- Тестируют удалённые или неиспользуемые сервисы/методы.
- Используют старые интерфейсы репозиториев (методы, которые переименованы/удалены).
- Проверяют детали реализации (например, какие SQL запросы выполняются), а не поведение.

#### 4.4. Тесты, форсирующие деградацию production-кода (critical)
Это тесты, ради которых в прод-коде:
- убирают `async` (возвращаются к синхронным вызовам);
- возвращают старые контракты API (поддерживают устаревшие версии без необходимости);
- сохраняют legacy-интерфейсы только для одного теста;
- добавляют compatibility‑hacks, ломающие типизацию;
- упрощают архитектуру (склеивают слои);
- возвращают deprecated поведение (например, старый алгоритм расчёта).

Такие тесты получают метку **`ARCHITECTURE_CONFLICT`** или **`LEGACY_LOCKING_TEST`**.

#### 4.5. Тесты с устаревшими mocks / fakes
- Мокают объекты, которых больше нет в архитектуре.
- Используют mock старых интерфейсов (несовместимые сигнатуры).
- Подменяют поведение, не существующее в production.
- Fake-репозитории с несовместимыми контрактами (возвращают `int`, а нужно `UUID`).

### 5. Формат результата аудита

Результат оформляется в файл `TODO/TASK_036_test_audit_Arch_report.md` со следующей структурой:

#### 5.1. Общая статистика
- Всего проанализировано тестов: `N`
- Найдено архитектурно-некорректных тестов: `M` (из них с меткой `ARCHITECTURE_CONFLICT`: `K`)

#### 5.2. Таблица нарушений (Architectural Test Mismatch)

| Test File | Problem | Conflicts With | Recommended Action | Priority |
|-----------|---------|----------------|--------------------|----------|
| `tests/test_users.py` | uses int ids (1, 2) | UUID architecture | rewrite fixtures to generate UUID | high |
| `tests/test_loader.py` | calls sync wrapper `run_sync` | async-only pipeline | migrate test to async, remove wrapper | critical |
| `tests/test_api.py` | sync `TestClient` | async FastAPI | replace with `AsyncClient` | high |

#### 5.3. Детализированный список нарушений (по категориям)

Для каждого теста указать:
- что именно устарело (конкретный вызов, тип, контракт);
- чему противоречит (текущей архитектуре / контрактам / типам данных / async модели);
- метку: `REWRITE_REQUIRED` / `DELETE_REQUIRED` / `MIGRATION_REQUIRED`.

Пример:
```
## Sync/Async violations
- `test_order_service.py:45` – вызывает `order_service.calculate()` (синхронно), а метод стал `async`. Рекомендация: добавить `await` и сделать тест `async def`. (REWRITE_REQUIRED)

## UUID vs Integer
- `test_user_factory.py:22` – фикстура генерирует `user_id = 1`. Противоречит модели User (UUID). Рекомендация: заменить на `uuid4()`. (MIGRATION_REQUIRED)


#### 5.4. Особо отмеченные случаи (Legacy Locking Tests)
Список тестов, которые заставляют сохранять legacy-поведение или мешают рефакторингу. Для каждого описать:
- какой именно рефакторинг блокируется;
- предлагаемое решение (переписать или удалить тест).

#### 5.5. План исправлений (по типам действий)

**Rewrite Required** – тесты, которые необходимо переписать под текущую архитектуру (блокируют развитие, но ценны).  
**Delete Required** – тесты, проверяющие удалённую логику, deprecated контракты или не имеющие ценности после изменений.  
**Migration Required** – тесты, требующие миграции на async / UUID / новые контракты API (можно выполнить постепенно).

#### 5.6. Рекомендации по автоматизации
- Внедрить линтеры: `ruff` с правилами на асинхронность в тестах, `mypy` для проверки типов в тестовом коде.
- Добавить CI-шаг, который запрещает:
  - использование `int` в качестве ID в тестовых файлах (регулярное выражение);
  - синхронные клиенты (`requests`, `TestClient` без async).
- Создать кастомную проверку на `async_to_sync` в прод-коде.

### 6. Критерии приёмки аудита
- Отчёт содержит конкретные указания на файлы, строки, имена тестов.
- Каждое нарушение обосновано ссылкой на актуальный production-код (или архитектурное решение).
- В отчёте нет предложений изменять production-архитектуру под тесты (только корректировка тестов или их удаление).
- Приведены не менее 3 примеров с категорией `ARCHITECTURE_CONFLICT`.
- Отчёт включает оценку приоритетов (high/medium/low) исправления каждого нарушения.

### 7. Исполнители и сроки (пример)
- **Исполнители:** Backend Architect (контроль инвариантов) + Senior Python Reviewer (скрининг кода) + Lead QA (стратегия тестирования).
- **Срок:** 3 рабочих дня на анализ, 1 день на подготовку отчёта.

### 8. Приложение – чек-лист быстрой проверки для аудитора
- [ ] Нет вызовов синхронных обёрток над async функциями в тестах.
- [ ] Все тесты, вызывающие async-функции, помечены `@pytest.mark.asyncio` и используют `await`.
- [ ] В тестах нет целочисленных ID (1, 42) в фикстурах, `parametrize`, `assert`.
- [ ] Для FastAPI эндпоинтов используется `AsyncClient`.
- [ ] Тесты не проверяют внутренние SQL-запросы или детали реализации репозиториев.
- [ ] Нет моков, которые ссылаются на удалённые классы/методы.
- [ ] Ни один тест не требует добавления `sync`-версии сервиса.
- [ ] В CI нет «хаков», позволяющих запускать синхронные тесты в async-окружении.
