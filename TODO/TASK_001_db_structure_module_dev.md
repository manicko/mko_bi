# Задание: подготовка ТЗ на модуль воспроизведения структуры

## Состав команды для выполнения задания
- **Backend Architect** – определяет перечень требуемых баз (основная, тестовая, иные) и архитектурные требования к воспроизведению.
- **Senior Python Developer** – выполняет поиск и анализ кода (репозитории, модели, миграции, конфиги), документирует схему БД.
- **DevOps / DB Admin** – проверяет окружения (dev/stage/prod), права, переменные окружения.
- **QA Engineer** – проверяет, что тестовая БД изолирована и соответствует схеме, участвует в валидации модуля воспроизведения.

---

## 1. Цель задания
**Составить техническое задание** на написание Python-модуля, который автоматически создаст/воспроизведёт точно такую же структуру баз (с возможностью отключения авто-миграций на проде) на целевом сервере и который можно будет запустить при первом старте FastAPI 

ТЗ должно содержать:

#### 2.2.1. Имя и расположение модуля
Пример: `src/db/starter.py`, вызывается из `main.py:lifespan`.

#### 2.2.2. Функциональные требования
- **Определение окружения** (production / staging / development / test) через переменную `ENV`.
- **Проверка существования БД** по DSN из переменной окружения (`MAIN_DATABASE_URL`, `TEST_DATABASE_URL`). Если база не существует – **не создавать её автоматически** (кроме тестовой), а выдать ошибку.
- **Проверка наличия схемы** (например, наличие таблицы `alembic_version` или кастомной `schema_version`). Если схема отсутствует:
  - в development/test + при `AUTO_MIGRATE=true` – применить миграции (через `alembic upgrade head`);
  - в production – выкинуть исключение с инструкцией (`Run migrations manually`).
- Для **тестовой БД** (`TEST_DATABASE_URL`) разрешено полностью пересоздавать базу (`DROP DATABASE ... WITH (FORCE); CREATE DATABASE ...;`) при запуске тестов (опциональный флаг `--recreate-db`).
- **Идемпотентность**: повторный запуск модуля не должен менять существующую схему (миграции применяются только если это необходимо).
- **Логирование**: каждый шаг логировать (INFO/ERROR).

#### 2.2.2.1. Требования безопасности для production

Модуль НЕ должен:

- автоматически создавать production БД;
- автоматически делать destructive migrations;
- автоматически DROP/RESET production schema;
- silently изменять production структуру.

В production:
- любые schema changes должны быть явными;
- при отсутствии схемы модуль должен:
  - завершиться ошибкой;
  - вывести инструкцию для ручного запуска миграций.

Любые destructive operations:
- разрешены только для test environment;
- должны требовать explicit flag/confirmation.

#### 2.2.3. Конфигурация через переменные окружения
Перечислить все переменные, которые модуль должен считывать (пример):
- `ENV=production|staging|development|test`
- `MAIN_DATABASE_URL=postgresql+asyncpg://...`
- `TEST_DATABASE_URL=...` (опционально)
- `AUTO_MIGRATE=true/false` (по умолчанию false в production)
- `MIGRATION_SCRIPT_PATH=alembic` (путь к миграциям)
- `LOAD_TEST_FIXTURES=true/false` (для тестовой БД)

#### 2.2.4. Требования к реализации
- Использовать `SQLAlchemy` (асинхронный движок) или `asyncpg` напрямую.
- Для миграций – интегрировать `Alembic` (выполнять команду через `subprocess` или API `alembic.command`).
- Для тестовой БД: предоставить возможность пересоздать базу без перезапуска контейнера (команда `python -m src.db.reset_test_db`).
- Не требовать ручного вмешательства для dev-окружений.

#### 2.2.4.1. Требования к async compatibility

Модуль воспроизведения БД должен:

- корректно работать в async FastAPI приложении;
- не блокировать event loop;
- использовать async-compatible DB connections;
- корректно закрывать соединения;
- поддерживать lifespan FastAPI.

Проверить:
- отсутствие sync SQLAlchemy engine внутри async runtime;
- отсутствие blocking subprocess calls внутри request lifecycle;
- корректное ожидание завершения миграций.

Если Alembic запускается через subprocess:
- запуск должен происходить только во время startup/lifespan;
- не внутри request handlers.

Результат:
- описание async-safe стратегии запуска миграций.

#### 2.2.5. Тестирование модуля
Написать тесты, проверяющие:
- при пустой БД в dev – миграции применяются;
- при повторном запуске – повторно не применяются;
- в production без схемы – поднимается ошибка;
- тестовая БД пересоздаётся по требованию.

#### 2.2.6. Документация
В `README.md` или `docs/db_setup.md` описать:
- как вручную создать базы (скрипт `scripts/create_dbs.sh`);
- как настроить переменные окружения для автовоспроизведения;
- как запустить миграции вручную (`alembic upgrade head`);
- как пересоздать тестовую БД.
