# Техническое задание на аудит тестового покрытия  
## «Выявление расхождений тестов с текущей архитектурой»

### 1. Цель аудита

Обнаружить тесты, которые **не соответствуют актуальной архитектуре** приложения (FastAPI + PostgreSQL).  
Расхождение проявляется в том, что тесты:

- используют устаревшие **синхронные/асинхронные контракты**;
- оперируют **неверными типами данных** (например, `int` вместо `UUID`);
- проверяют **неактуальные контракты** API, DTO, репозиториев;
- **противоречат текущей реализации** и вынуждают изменять production-код ради прохождения.

> **Принцип:** архитектура и код production — источник истины.  
> Тесты должны адаптироваться под них, а не наоборот.

### 2. Объект аудита

- Все тесты (unit, integration, API, e2e);
- Фикстуры, фабрики данных, моки, хелперы;
- Конфигурация тестового окружения (event loop, HTTP clients, БД);
- CI‑пайплайн запуска тестов.

### 3. Эталон архитектуры (что считать правильным)

Аудитор фиксирует **текущее состояние** production‑кода по следующим аспектам:

| Аспект | Эталон (берётся из реализации) |
|--------|--------------------------------|
| **Синхронность** | Тип функций (async/def) для каждого публичного метода сервиса, репозитория, хендлера. |
| **Идентификаторы** | Тип первичных/внешних ключей в моделях БД (`UUID` или `Integer`). |
| **API клиент** | Используется ли в приложении асинхронный (`AsyncClient`) или синхронный клиент. |
| **DTO / Pydantic** | Актуальные поля и типы в схемах запросов/ответов. |
| **Слои** | Где находится бизнес-логика (в сервисах, не в роутах). |

Аудитор **не оценивает правильность архитектуры** — только соответствие тестов этой архитектуре.

### 4. Категории расхождений (что искать в тестах)

#### 4.1. Sync / Async mismatch
- Тест вызывает функцию синхронно, но она `async def` (и наоборот).
- Для асинхронного API используется синхронный `TestClient` (или наоборот).
- Отсутствует `await` при вызове async‑функции.
- Используется `asyncio.run()` или `async_to_sync` в тесте для обхода жизненного цикла.
- В production‑код добавлена синхронная обёртка только ради теста.

#### 4.2. Типы данных
- В тестах используется `int` вместо `UUID` (фикстуры, параметризация, assert).
- Тип данных поля в тесте (например, `str` для даты) не совпадает с production‑моделью.
- Тест опирается на устаревшую версию DTO (лишние/отсутствующие поля).

#### 4.3. Контракты и архитектура слоёв
- Тест ожидает бизнес‑логику внутри роутера (фактически логика вынесена в сервис).
- Тест напрямую обращается к БД в обход репозитория (хотя production использует репозиторий).
- Тестируется удалённый или переименованный метод/сервис.
- Проверяются детали реализации (конкретные SQL‑запросы, вызовы внутри функции) вместо поведения.

#### 4.4. Тесты, ломающие архитектуру (critical)
Такие тесты **уже привели** (или могут привести) к деградации production‑кода:
- из‑за теста убрали `async`;
- вернули старый контракт API;
- сохранили legacy‑интерфейс только для одного теста;
- добавили compatibility‑хак, упрощающий архитектуру.

Каждый такой случай получает метку **`ARCHITECTURE_CONFLICT`**.

#### 4.5. Устаревшие моки / fakes
- Мок объекта, который удалён или переименован.
- Mock интерфейса с несовместимой сигнатурой.
- Fake‑репозиторий возвращает `int`, а production возвращает `UUID`.

Пример:

## Sync/Async mismatches
- `test_service.py:42` – вызывает `repo.get()` без `await`, хотя `get` – async.

#### 5.4. Legacy Locking Tests (особо критические)
- Какой рефакторинг блокируется (например, переход на async, замена int на UUID)
- Предлагаемое решение (переписать тест, удалить, заменить подход)

#### 5.5. План исправлений

- **Rewrite Required** – тесты ценные, но несовместимые; переписать под текущую архитектуру.
- **Delete Required** – тесты проверяют удалённую логику или deprecated контракты.
- **Migration Required** – требуют поэтапной миграции (например, все тесты с int → UUID).

#### 5.6. Автоматизация (рекомендации)

- Линтер `ruff` с правилами:
  - запрет `async_to_sync` в тестах;
  - запрет `TestClient` для async‑приложений;
  - запрет числовых ID в тестовых файлах (регулярка `\b[0-9]+\b` в `id=`).
- CI‑шаг, проверяющий, что тесты не используют синхронные обёртки.
- `mypy` для проверки типов в тестовом коде (включить `--check-untyped-defs`).

### 8. Чек‑лист аудитора (быстрая проверка)

- [ ] Нет вызовов `async_to_sync` или `asyncio.run()` в тестах.
- [ ] Все тесты, вызывающие async‑функции, имеют `@pytest.mark.asyncio` и `await`.
- [ ] В тестах нет целочисленных ID (1, 42) — только UUID.
- [ ] API‑тесты используют `AsyncClient`, если приложение асинхронное.
- [ ] Тесты не проверяют внутренние SQL‑запросы напрямую.
- [ ] Моки ссылаются только на существующие классы/методы.
- [ ] Ни один production‑метод не имеет синхронного дублёра ради теста.
