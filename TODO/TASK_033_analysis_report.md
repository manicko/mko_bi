## 2. Архитектурные проблемы

### 2.1. Критические (требуют немедленного исправления)

#### 2.1.1. Синтаксическая ошибка в upload.py (линия 89)
**Файл:** `src/mko_bi/api/routes/upload.py:89`  
**Проблема:** Использование `await` в синхронной функции:
```python
# НЕПРАВИЛЬНО - функция не объявлена как async
def upload_file_endpoint(...):
    ...
    try:
        file_content = file.read()
    except TypeError:
        file_content = await file.read()  # await в sync функции!
```
**Последствия:** Приложение не запустится или упадет при загрузке файла.  
**Решение:** Сделать функцию асинхронной или использовать sync-чтение.

#### 2.1.2. Синтаксическая ошибка в тестах (линии 672-673)
**Файл:** `tests/services/test_data_service.py:672-673`  
**Проблема:** Лишние отступы (12 пробелов) без блока кода:
```python
def test_get_dashboard_aggregates_success(self, db_session):
    dashboard_id = uuid.uuid4()
    graph_id = uuid.uuid4()


            result = get_dashboard_aggregates(...)  # 12 пробелов!
```
**Последствия:** Ошибка синтаксиса, тесты не запускаются.  
**Решение:** Удалить лишние отступы, добавить недостающий `with patch()` блок.

#### 2.1.3. Потеря данных при обработке
**Места:** `data_service.py`, `_task_statuses`  
**Проблема:** Статусы задач и результаты обработки хранятся в памяти (глобальный dict), а не в БД.  
**Последствия:** Потеря данных при перезапуске сервера, невозможность масштабирования.  
**Решение:** Сохранять статусы в таблицу `processing_logs` или отдельную таблицу статусов.

#### 2.1.4. Агрегированные данные не сохраняются в БД
**Места:** `data_service.py`, `_process_csv_file()`  
**Проблема:** Результаты обработки возвращаются клиенту, но не сохраняются в таблицу `aggregated_data`.  
**Последствия:** Дашборды не могут отображать данные, таблица `aggregated_data` всегда пуста.  
**Решение:** Добавить сохранение через `AggregatedDataRepository` после обработки.

### 2.2. Серьезные (нарушение архитектурных принципов)

#### 2.2.1. Бизнес-логика в API-роутах
**Примеры:**
- `dashboards.py`: Проверка прав, создание дашборда прямо в эндпоинте
- `users.py`: Логика обновления пользователя в роуте
- `auth.py`: Rate-limiting, логика аутентификации

**Нарушение:** Single Responsibility Principle, смешение уровней.  
**Решение:** Вся бизнес-логика должна быть в `services/`, роуты только координируют.

#### 2.2.2. Прямое использование сессии БД в роутах
**Примеры:**
- `dashboards.py:183`: `DashboardRepository.get(dashboard_id, db)` 
- `users.py:165`: `UserRepository.get(user_id, db)`

**Нарушение:** Слои напрямую зависят от БД, нет абстракции.  
**Решение:** Использовать сервисы, которые уже инкапсулируют работу с репозиториями.

#### 2.2.3. Циклические зависимости (риск)
**Примеры:**
- `services/data_service.py` → `core/permissions.py` → `db/repositories/` → `models/` → `services/`
- `api/deps.py` → `core/permissions.py` → `db/session.py`

**Последствия:** Проблемы с импортами, сложность тестирования.  
**Решение:** Внедрить Dependency Injection, использовать интерфейсы.

#### 2.2.4. Глобальное состояние
**Места:** 
- `config.py`: Глобальный `config = Config()`
- `data_service.py`: `_task_statuses: dict[uuid.UUID, dict]`
- `session.py`: Глобальный `engine`, `SessionLocal`

**Нарушение:** Сложность тестирования, race conditions.  
**Решение:** Использовать контекст/синглтон с явным управлением жизненным циклом.

### 2.3. Умеренные (нарушение best practices)

#### 2.3.1. Отсутствие интерфейсов
**Проблема:** Нет абстрактных классов для репозиториев, сервисов.  
**Последствия:** Невозможно заменить реализацию (например, PostgreSQL → MongoDB).  
**Решение:** Создать `interfaces/` с ABC для каждого слоя.

#### 2.3.2. Нарушение Dependency Inversion
**Пример:** `dashboards/implementations/dashboard_1.py` зависит от конкретных чартов.  
**Решение:** Внедрять чарты через конструктор (DI).

#### 2.3.3. Слабая изоляция слоев
**Пример:** `dashboards/base.py` импортирует `DashboardConfig` из `models/`.  
**Решение:** Слой `dashboards` не должен зависеть от `models` (зависит от домена).

## 3. Проблемы в коде (Code Quality)

### 3.1. Обработка ошибок

#### 3.1.1. Пустые except (Critical)
**Места:** 
- `security.py:115`: `except Exception as e:` без `from e`
- `auth_service.py:42`: `raise ValueError(...)` без `from err`
- `dashboard_service.py:51`: `raise ValueError(...)` без `from err`

**Последствия:** Потеря стека вызовов, сложность дебаггинга.  
**Исправление:** Добавить `from e` или `from None`.

#### 3.1.2. Нет логирования ошибок
**Места:** 
- `upload.py:121`: `except Exception as e:` - логирует, но не пробрасывает оригинал
- `data_service.py`: Много мест с голым `except Exception`

**Исправление:** Логировать с `logger.exception()` или `raise ... from e`.

#### 3.1.3. Неправильные статус-коды
**Места:** 
- `upload.py:103`: `raise HTTPException(500, ...)` при любой ошибке
- Нет дифференциации между 4xx и 5xx

**Исправление:** Четкое разделение: 400 для валидации, 403 для прав, 500 для сервера.

### 3.2. Транзакции и БД

#### 3.2.1. Нет явных транзакций
**Места:** 
- `dashboard_service.py:create_dashboard()`: Создает дашборд, затем дает права
- Если права не дадут, дашборд останется (частичное выполнение)

**Решение:** Обернуть в `with db.begin():` или явный `db.begin()`/`commit()`/`rollback()`.

#### 3.2.2. Race conditions
**Места:** 
- `auth_service.py:_validate_email_uniqueness()`: Проверка + вставка не атомарны
- `dashboard_service.py:create_dashboard()`: То же самое

**Решение:** Использовать `SELECT FOR UPDATE` или UNIQUE constraints + обработку IntegrityError.

#### 3.2.3. Утечки сессий
**Места:** 
- `core/permissions.py:check_dashboard_access()`: Создает `SessionLocal()`, но `finally: db.close()` может не выполниться при return
- `data_service.py`: Много мест с `db = SessionLocal()` без гарантии закрытия

**Решение:** Использовать контекстный менеджер или `try/finally` со 100% гарантией.

### 3.3. Безопасность

#### 3.3.1. SQL-инъекции (Low risk)
**Места:** 
- `data_service.py:_process_csv_file()`: Фильтры применяются через `pl.col(field)`
- Если `field` приходит от пользователя - риск инъекции в Polars

**Решение:** Валидировать `field` по белому списку.

#### 3.3.2. Инъекции в CSV
**Места:** 
- `data_service.py`: Читает CSV без валидации структуры
- Может содержать формулы, скрипты

**Решение:** Использовать `safe` режим Polars, валидировать каждую ячейку.

#### 3.3.3. Нет rate limiting (кроме auth)
**Места:** 
- `auth.py`: Есть rate limit на логин
- Остальные эндпоинты: Нет

**Решение:** Добавить middleware или dependency для rate limiting.

#### 3.3.4. Хардкод секретов
**Места:** 
- `config.py`: `JWT_SECRET_KEY` по умолчанию = "your-secret-key-change-in-production"
- `db.py`: Пароль по умолчанию = "1234"

**Решение:** Обязательные env-переменные, запрет дефолтных секретов.

### 3.4. Работа с файлами

#### 3.4.1. Незакрытые дескрипторы (Critical)
**Места:** 
- `data_service.py:_save_uploaded_file()`:
```python
with open(file_path, "wb") as f:
    f.write(file_content)  # OK
# Но если ошибка после записи - файл не удаляется
```
- `cleanup_task_files()`: Не вызывается нигде!

**Последствия:** Утечки дискового пространства, orphaned files.  
**Решение:** `try/finally` с гарантированным удалением, вызов `cleanup_task_files()`.

#### 3.4.2. Не удаляется временный файл при ошибке
**Места:** `upload_file()`: Если валидация падает, файл остается.  
**Решение:** Сохранять после валидации или удалять в `finally`.

#### 3.4.3. Path traversal
**Места:** `upload_file()`: `filename` используется как есть  
**Решение:** Проверять `Path(filename).name == filename`.

### 3.5. Производительность

#### 3.5.1. Загрузка всего CSV в память
**Места:** `upload.py:86`: `file_content = file.read()`  
**Проблема:** 100MB файл → 100MB RAM × одновременных запросов  
**Решение:** Стриминг, chunked upload, лимит размера.

#### 3.5.2. N+1 запросов
**Места:** `data_service.py:get_dashboard_aggregates()`: 
```python
graphs = db.query(Graph).filter(...).all()
for graph in graphs:
    aggregates = db.query(AggregatedData).filter(...).all()  # N+1!
```
**Решение:** Использовать `joinedload()` или один запрос с GROUP BY.

#### 3.5.3. Нет batch-обработки
**Места:** `data_service.py:_process_csv_file()`: Весь DataFrame в память  
**Решение:** Использовать `pl.scan_csv()` для ленивой загрузки.

### 3.6. Конфигурация

#### 3.6.1. Хардкод путей
**Места:** 
- `config.py`: `UPLOAD_TEMP_DIR = "data/tmp_uploads"`
- `db.py`: `sqlite:///:memory:` для тестов

**Решение:** Все через env-переменные.

#### 3.6.2. Нет валидации конфига
**Места:** `config.py`: `DB_PORT = int(os.getenv("DB_PORT", "5432") or "5432")`  
**Проблема:** Если `DB_PORT=abc` → `ValueError` при импорте  
**Решение:** Валидация с `pydantic-settings`.

### 3.7. Типизация

#### 3.7.1. Использование Any
**Места:** 
- `config.py`: `def get(self, key: str, default: Any = None) -> Any`
- `data_service.py`: `result_data: dict[str, Any]`
- `dashboards/`: `config: DashboardConfig` → `dict` везде

**Решение:** Конкретные типы или `TypeVar`.

#### 3.7.2. Нет Optional где нужно
**Места:** 
- `dashboard_service.py:get_dashboard()`: Возвращает `DashboardRead`, но может быть `None`
- `db/models/`: `layout_id: UUID | None`, но не везде

**Решение:** Добавить `| None` где нужно.

### 3.8. Документация

#### 3.8.1. Отсутствуют docstring
**Места:** 
- `dashboards/implementations/dashboard_2.py`: Частично
- `db/repositories/`: У классов есть, у методов часто нет

**Решение:** Добавить Google-style docstrings.

#### 3.8.2. Непонятные названия
**Места:** 
- `_truncate_password()`: OK
- `_validate_config()`: OK
- Но `_check_owner_permission()` → на самом деле проверяет `admin`, не владельца

**Решение:** `_is_admin_permission()`.

### 3.9. Дублирование

#### 3.9.1. Дублирующийся код
**Места:** 
- `auth.py` и `core/permissions.py`: Оба имеют `get_current_user()`
- `dashboards.py` и `services/dashboard_service.py`: Оба создают дашборды
- Валидация email/роли в `auth_service.py` и `user_service.py`

**Решение:** Вынести в утилиты/сервисы.

#### 3.9.2. Копипаста паттернов
**Места:** 
- Все роуты: `try/except` блоки почти одинаковые
- Все репозитории: `get/create/update/delete` одинаковы

**Решение:** Базовые классы, декораторы, миксины.

### 3.10. Неиспользуемый код

#### 3.10.1. Dead code
**Места:** 
- `dashboards/registry.py`: `@register` декоратор не используется
- `models/data.py`: `DataUpload`, `LoaderConfig` - не импортируются
- `db/models/access.py`: `Access` alias - не используется
- `db/models/user.py`: `__str__` - не используется

**Решение:** Удалить или использовать.

#### 3.10.2. Пустые файлы/заглушки
**Места:** 
- `src/mko_bi/data/logs/`: Пустая директория
- `src/mko_bi/__init__.py`: Пустой
- `api/__init__.py`: Пустой

**Решение:** Удалить или добавить `__all__`.

### 3.11. Проблемы typing (mypy)

**Главные ошибки:**
1. `F821 Undefined name` в моделях БД (forward references не разрешены)
2. `Missing type arguments for generic type "dict"` (31 место)
3. `Incompatible types in assignment` (zip() возвращает Sequence, а не list)
4. `Name "Dashboard" is not defined` (циклические импорты в моделях)

**Решение:** 
- Использовать `from __future__ import annotations`
- Добавить `dict[str, Any]` вместо `dict`
- Приводить типы: `list(zip(...))`
- Разрешить циклические импорты через строки или `TYPE_CHECKING`
