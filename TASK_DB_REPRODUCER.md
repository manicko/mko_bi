# Техническое задание на модуль воспроизведения структуры базы данных

## 1. Имя и расположение модуля
Модуль должен располагаться по пути: `src/db/starter.py`
Модуль должен быть вызван из `main.py` в событии `lifespan` (startup).

## 2. Функциональные требования
### 2.1 Определение окружения
- Окружение определяется по переменной `ENV` (значения: `production`, `staging`, `development`, `test`).
- Если переменная `ENV` не установлена, считается окружение `development`.

### 2.2 Проверка существования БД
- Модуль получает строку подключения (DSN) из переменной окружения:
  - Для основной БД: `MAIN_DATABASE_URL` (обязательна)
  - Для тестовой БД: `TEST_DATABASE_URL` (опционально, используется только если `ENV=test`)
- Если БД не существует:
  - Для `ENV=test` и при наличии флага `--recreate-db` (или переменной `RECREATE_TEST_DB=true`) – разрешено создать БД.
  - Для всех остальных окружений – модуль НЕ создает БД автоматически и завершается с ошибкой, указывая на необходимость ручного создания БД.

### 2.3 Проверка наличия схемы
- Считается, что схема присутствует, если в БД существует таблица `alembic_version`.
- Если схема отсутствует:
  - В окружениях `development` и `test` при условии `AUTO_MIGRATE=true` – применить миграции (через `alembic upgrade head`).
  - В окружении `production` – завершиться с ошибкой и вывести инструкцию: "Run migrations manually: alembic upgrade head".
  - В окружении `staging` – поведение такое же, как в `production` (по умолчанию без авто-миграций).

### 2.4 Идемпотентность
- Повторный запуск модуля не должен применять миграции, если схема уже актуальна (т.е. если текущая версия схемы совпадает с последней версией в скриптах миграций).
- Миграции применяются только если целевая версия (head) отличается от текущей.

### 2.5 Логирование
- Каждый шаг должен быть залогирован с использованием стандартного модуля `logging`:
  - INFO: начало шага, успешное выполнение.
  - ERROR: ошибки и предупреждения.
- Примеры сообщений:
  - "Checking database existence for URL: {url}"
  - "Database exists."
  - "Schema version table not found. Applying migrations..."
  - "Migrations applied successfully."
  - "Database schema is up to date."
  - "ERROR: Database does not exist. Please create it manually."
  - "ERROR: Schema is missing and AUTO_MIGRATE is false. Run migrations manually."

## 3. Требования безопасности для production
В окружении `production` модуль НЕ должен:
- Автоматически создавать базу данных.
- Автоматически выполнять разрушительные миграции (например, dropping tables, колонок).
- Автоматически сбрасывать или изменять схему базы данных без явного указания.
- Молчаливо изменять структуру production БД.

Если схема отсутствует в production:
- Модуль должен завершиться с ошибкой уровня CRITICAL.
- Вывести четкую инструкцию для администратора: "Schema is missing. Please run migrations manually using 'alembic upgrade head'."

## 4. Конфигурация через переменные окружения
Модуль должен читать следующие переменные окружения:
- `ENV` – окружение (production/staging/development/test), по умолчанию development.
- `MAIN_DATABASE_URL` – строка подключения к основной БД (обязательна).
- `TEST_DATABASE_URL` – строка подключения к тестовой БД (опционально, используется только если ENV=test).
- `AUTO_MIGRATE` – флаг, разрешающий автоматическое применение миграций в dev/test (значения: true/false), по умолчанию false в production и staging, true в development и test? (уточнить: в задании сказано, что в development/test при AUTO_MIGRATE=true – применять миграции; значит по умолчанию в development/test может быть false, но мы можем установить true в dev для удобства).
- `MIGRATION_SCRIPT_PATH` – путь к каталогу с миграциями Alembic (по умолчанию "alembic", расположенный в корне проекта).
- `RECREATE_TEST_DB` – флаг для пересоздания тестовой БД (значения: true/false), по умолчанию false.
- `LOG_LEVEL` – уровень логирования (по умолчанию INFO).

## 5. Требования к реализации
### 5.1 Общие требования
- Использовать асинхронный движок SQLAlchemy (или asyncpg напрямую) для проверки существования БД и схемы.
- Для применения миграций использовать Alembic:
  - Предпочтительно через API `alembic.command` (если возможно в асинхронном контексте).
  - Если используется `subprocess`, то запуск должен происходить только в событии startup FastAPI (не внутри request handlers) и должен быть ожидаемым (await).
- Обеспечить корректное закрытие всех соединений и освобождение ресурсов.
- Модуль должен быть idempotent и безопасным для повторных запусков.

### 5.2 Требования к async compatibility
- Модуль должен корректно работать в асинхронном FastAPI приложении.
- Не блокировать event loop:
  - При использовании `subprocess` для Alembic – запускать в отдельном потоке или процессе с использованием `asyncio.create_subprocess_exec` и await.
  - При проверке существования БД и схемы – использовать асинхронные драйверы (asyncpg или async SQLAlchemy).
- Корректно закрывать соединения после использования.
- Поддерживать паттерн lifespan FastAPI (async def startup(): ... и async def shutdown(): ...).

### 5.3 Структура модуля
- Функция `check_database_exists(dsn: str) -> bool` – проверяет, существует ли БД по данному DSN.
- Функция `check_schema_applied(engine) -> bool` – проверяет наличие таблицы `alembic_version`.
- Функция `apply_migrations() -> None` – применяет миграции Alembic.
- Функция `recreate_test_db(dsn: str) -> None` – удаляет и создает тестовую БД (если разрешено).
- Основная функция `init_db()` – orchestrates все шаги в соответствии с окружением и настройками.

## 6. Тестирование модуля
Написать юнит-тесты (используя pytest) для проверки:
- При пустой БД в окружении development с `AUTO_MIGRATE=true` – миграции применяются.
- При повторном запуске в той же среде – миграции не применяются повторно.
- В окружении production без схемы – поднимается ошибка (например, `RuntimeError` с сообщением о необходимости запустить миграции вручную).
- Тестовая БД пересоздается по флагу `RECREATE_TEST_DB=true` (или `--recreate-db`).
- Логирование содержит ожидаемые сообщения на каждом этапе.
- Модуль не блокирует event loop при работе в async контексте.

## 7. Документация
В файле `docs/db_setup.md` описать:
- Как вручную создать базы данных (пример скрипта `scripts/create_dbs.sh`).
- Как настроить переменные окружения для автовоспроизведения структуры БД.
- Как запустить миграции вручную: `alembic upgrade head`.
- Как пересоздать тестовую БД (например, через команду `python -m src.db.starter --recreate-test-db` или через флаг в переменных окружения).

## 8. Пример использования
В `main.py`:
```python
from src.db.starter import init_db

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Инициализация БД при старте
    await init_db()
    yield
    # Здесь можно добавить очистку при shutdown, если потребуется

app = FastAPI(lifespan=lifespan)
```

## 9. Критерии приёмки
- Модуль корректно определяет окружение и действует согласно требованиям.
- В production модуль не выполняет никаких автоматических изменений схемы и требует явного применения миграций.
- Логирование охватывает все ключевые шаги и ошибки.
- Модуль является idempotent.
- Все асинхронные операции не блокируют event loop.
- Наличие unit-тестов, покрывающих указанные сценарии.
